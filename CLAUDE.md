# MarkusCraft

A personalized voxel sandbox game that runs in the browser. The genre is "block-building
game in a procedurally generated world"; everything in it is original work.

## Vision

- First-person voxel world: explore procedurally generated terrain, break and place blocks.
- Runs as a static site (GitHub Pages), no server, desktop browsers with keyboard + mouse.
- Built in three phases, each planned with the owner and then implemented autonomously:
  1. **Core** – chunked terrain, movement and collision, break/place, day/night, basic UI
     (plan: `docs/phase-1-plan.md`)
  2. **Gameplay** – inventory/hotbar, saving/loading, further mechanics (not yet planned)
  3. **Personalization** – custom blocks, textures, characters, names, effects (not yet planned)

## Hard rules

1. **No third-party game assets.** Never use Minecraft/Mojang assets, textures, sounds,
   logos, fonts or proper names, and do not copy their look pixel for pixel. All textures
   are generated by code in this repo. No binary art assets are committed (test reference
   screenshots are the only images in the repo).
2. **The repo is the only memory.** Every cloud session starts from a fresh clone. Anything
   a later session needs (decisions, deviations, how to run things) must be committed in
   `CLAUDE.md` or `docs/`.
3. **Autonomous implementation.** Planning sessions are interactive; implementation sessions
   are not. During implementation never ask the owner a question. If something is
   ambiguous, choose the simplest option consistent with the phase plan and record it in the
   phase report (`docs/phase-N-report.md`, section "Decisions and deviations").
4. **Commit frequently.** Commit after every completed plan step at the latest, and more
   often for larger steps. Every commit must pass `npm run check`. Push after each step.
   Write messages as `<area>: <what changed>` (e.g. `world: add tree generation`).
5. **One branch + one PR per phase.** All work of a phase goes onto a single branch: the
   branch assigned to the cloud session if there is one, otherwise `phase-N-<name>`. When
   the phase meets the Definition of Done, open exactly one pull request into `main`.
   Never push to `main` directly. Merging is the owner's decision.
6. **Stay in scope.** Implement what the phase plan lists. Items under "Out of scope" are
   not to be built, even if they seem easy.

| Rendering          | Three.js (WebGL2)                                                   |
| Unit tests         | Vitest (Node environment)                                           |
| Browser tests      | Playwright (`@playwright/test`), Chromium, software WebGL           |
| Lint / format      | ESLint (typescript-eslint) + Prettier                               |
| Package manager    | npm, lockfile committed                                             |
| Runtime            | Node 22 (`.nvmrc`)                                                  |
| CI / deploy        | GitHub Actions: checks on every push, deploy `main` to GitHub Pages |

Keep runtime dependencies minimal: `three` only, unless a phase plan says otherwise.
Noise, RNG, physics and meshing are implemented in this repo.

### Playwright in cloud sessions

The cloud container ships Playwright **1.63.0** with a matching Chromium under
`/opt/pw-browsers`. Pin `@playwright/test` to exactly that version and **never run
`playwright install`** in a cloud session. CI installs its own browser with
`npx playwright install --with-deps chromium`. If the preinstalled version has changed in
a later session, update the pin to match and regenerate the reference screenshots.

## Architecture and code conventions

- **Pure core, thin shell.** `world/`, `player/` and `util/` must not import `three` or
  touch the DOM (enforced by an ESLint `no-restricted-imports` rule). They are tested in
  Node. Only `render/`, `ui/`, `input/` and `game/` may use Three.js and browser APIs.
  The same rule covers `render/textures/tiles.ts`. The core may import `game/config.ts`.
- **Determinism.** No `Math.random()` and no `Date.now()` in `world/`, `player/`, `util/`
  or texture generation. Randomness comes from the seeded RNG; time comes in as a parameter.
  The same seed must always produce the same world and the same textures.
- **Fixed timestep.** Simulation runs at 60 Hz with an accumulator; rendering interpolates.
- **Coordinates.** Y is up. Block `(x, y, z)` occupies `[x, x+1) × [y, y+1) × [z, z+1)`.
  Chunk coordinates are `floor(x / 16)`, `floor(z / 16)`. One unit = one block.
- **Constants** (chunk size, speeds, reach, …) live in `src/game/config.ts`, not inline.
- **Style.** ES modules, named exports only, no `any` (use `unknown` and narrow), no
  non-null `!` without a comment, `camelCase` values, `PascalCase` types and classes,
  `SCREAMING_SNAKE_CASE` constants. Files are `camelCase.ts`, or `PascalCase.ts` when
  the file's main export is a class. Prettier decides formatting.
- **Comments** explain why, not what. Every module starts with a one-line purpose comment.
- **Hot paths** (meshing, generation, physics) avoid per-block allocations; use typed arrays.
- **In-game text** is English. Code, comments and docs are English.

## Headless testing

The game exposes a test API on `window.__mc` (`src/game/testApi.ts`) and accepts URL
parameters so tests are deterministic. Details are specified in `docs/phase-1-plan.md`
(section "Test strategy"). In short:

- `?seed=<int>` fixes the world, `?time=<0..1>` sets the time of day, `?freeze=1` stops
  the clock, `?test=1` runs without pointer lock and with fixed settings.
- In test mode the simulation only advances through `__mc.step(n)`; rendering and chunk
  loading keep running. Tests without `test=1` cover the start screen and the real loop.
- Tests wait on game state (`__mc.isReady()`, `__mc.whenIdle()`), never on fixed sleeps.
- `e2e/game.ts` opens the game and wraps the test API; `e2e/helpers.ts` measures pixels;
  `e2e/fixtures.ts` fails any test whose page logs a console error or warning.
- Every visual feature gets both a rule-based assertion (measurable pixel or state facts)
  and, where useful, a reference screenshot comparison (`e2e/screenshots/`).
- After changing anything visual, the implementing session must also open the produced
  screenshots with the Read tool and judge them by eye. For a quick look at any pose:
  `npm run build`, `npm run preview`, then `node scripts/shot.mjs "?test=1&seed=1337" out.png`.
- The full e2e run takes about two minutes; run long commands in the background.

## Definition of Done (per phase)

A phase is done when all of the following hold:

1. Every step of the phase plan is implemented and each acceptance criterion is met.
2. `npm run check:all` passes locally with zero warnings from TypeScript and ESLint.
3. CI is green on the phase branch.
4. New logic has unit tests; every user-visible feature has at least one Playwright test.
5. Reference screenshots are up to date, committed, and were looked at by the session.
6. The browser console shows no errors or warnings during the e2e run.
7. `CLAUDE.md` reflects the current structure, commands and conventions.
8. `docs/phase-N-report.md` exists: what was built, decisions and deviations from the
   plan, known issues, measured performance numbers, and suggestions for the next phase.
9. Hard rule 1 has been checked: no third-party assets or protected names anywhere.
10. One pull request into `main` is open, describing the result and linking the report.
